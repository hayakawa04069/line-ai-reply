# 予約データベースの設計・設定手順

このフォルダは準備用です。**ファイルを作成しただけではSupabaseに反映されません。**
既存のLINE AI返信、環境変数、Render設定は変更しません。

## 設計

初期版は1店舗・同時に1組、日本時間（Asia/Tokyo）固定です。

| テーブル | 保存する内容 |
| --- | --- |
| `customers` | 顧客ID、LINEユーザーID、表示名、任意の電話番号 |
| `menus` | メニュー名、所要時間、価格（円）、受付中かどうか |
| `reservations` | 顧客・メニュー、開始・終了日時、状態、予約時点のメニュー内容・料金 |
| `business_hours` | 曜日ごとの開店・閉店時刻。登録のない曜日は定休日 |
| `closed_days` | 祝日や臨時休業など、日付単位の休業日 |
| `booking_settings` | 店名、予約開始時刻の間隔、何日先まで予約可能か |
| `booking_admins` | 店舗管理者として許可するSupabase AuthユーザーのID |

予約状態は `confirmed`（確定）、`cancelled`（キャンセル）、`completed`（来店済み）です。
休憩時間・日付ごとの特別営業時間・日をまたぐ営業・複数スタッフ・複数同時受付は今回の対象外です。
受付間隔は開店時刻を基準にします。例えば10時開店で15分間隔なら、10:00、10:15、10:30…が開始時刻です。
営業時間や休業日を変更しても既存予約は削除されません。追加SQL `003_business_settings.sql` を適用すると、未終了の既存予約と矛盾する設定変更はDB側で拒否します。

## 二重予約を防ぐ仕組み

- PostgreSQLの排他制約で、キャンセル済み以外の予約の時間重複を禁止します。
- 10:00～11:00の予約がある場合、10:30～11:30は拒否し、11:00～12:00は許可します。
- 同時に複数の登録処理が走っても、DBが重複を拒否します。管理者からの変更にも適用されます。
- 予約作成・日時変更・キャンセルからの復活時には、過去日時、受付期間外、休業日、営業時間外、受付間隔外、無効なメニューを拒否します。
- メニューの所要時間から終了日時をDB側で計算します。料金もDB側の値を保存します。
- `request_id` の一意制約で、同じ確定リクエストの再送による重複を防ぎます。

後で作るAPIは、競合エラー `23P01` を「先に予約が入りました」と案内し、`23505` は同一リクエストの予約を本人確認後に再取得します。入力エラーは `23514` などを扱います。DBエラー本文を利用者にそのまま表示しないでください。
同じリクエストの再送では新しい `request_id` を作らず、同じIDを再利用する実装が必要です。
予約変更は1つのUPDATEとして実行します。変更に失敗した場合、元の予約は残ります。

## 個人情報の保護

全テーブルでRLS（行単位のアクセス制限）を有効にしています。

| アクセス元 | 権限 |
| --- | --- |
| 未ログイン・匿名キー | 全テーブルにアクセス不可 |
| 一般のSupabase Authユーザー | 顧客・予約などの行を参照・変更不可 |
| `booking_admins` に登録したログイン済み管理者 | 店舗データを参照・編集可能。予約の削除は禁止 |
| `service_role` / DB管理者 | RLSを迂回可能。サーバー・管理用途に限定 |

`booking_admins` はブラウザーから参照・変更できません。管理者の追加・削除はSQL Editorで行います。
Supabaseへのログインだけでは管理者になれません。

顧客向けAPIとLIFF認証は `booking/` に実装しています。お客様のブラウザーからDBへ直接予約を登録する設計ではありません。
サーバーでLINEのIDトークンを検証し、その本人に対応する顧客IDを決めます。ブラウザーが指定した顧客IDやLINEユーザーIDだけを信用しません。
空き状況APIは空き時間だけを返し、予約者名・電話番号・LINEユーザーIDを返しません。

`service_role`キーやDBパスワードはブラウザー・LIFF・GitHub・チャットに載せません。必要になった段階でサーバー専用のシークレットに登録します。通常の管理者操作はユーザーの認証情報を使い、RLSを適用します。
RLSはアクセス制御であり、列ごとの暗号化ではありません。実運用前に最小限の収集項目、保存期間・削除手順、利用者への案内、バックアップと復元を決めてください。電話番号は不要なら収集しません。
予約が残る顧客は誤削除を防ぐため削除できません。キャンセルは削除ではなく状態変更にします。個人情報の削除依頼には、関連データを確認したうえで匿名化などの手順を別途用意します。

## 営業設定画面用の追加SQL（003・まだSupabaseで実行しない）

`003_business_settings.sql` は、001・002が適用済みのDBへの追加変更です。
既存プロジェクトで001・002を再実行しないでください。まずテスト専用 `line-booking-test` での適用・検証を予定し、本番用 `line-booking-system` には適用しません。

追加内容：

- `booking_settings.settings_revision`：他担当者の設定を上書きしないためのUUID。
- `get_business_settings()`：設定全体を1つのJSONで取得する管理者専用関数。
- `save_business_settings(uuid, integer, jsonb, jsonb)`：版の一致・入力を検査し、設定・営業時間・休業日を1トランザクションで保存する管理者専用関数。
- 設定と既存予約の整合性検査、設定保存と予約書き込みの競合を防ぐロック用トリガー。予約検証・重複制約・RLSは解除しません。
- 予約・設定の書き込みをREAD COMMITTEDに限定する検査。PostgRESTの標準設定では変更不要です。

SECURITY INVOKERのため管理者本人の権限と既存RLSを使用します。公開・匿名の実行権限は取り消し、設定取得・保存関数の実行はauthenticatedのみに許可し、関数内部でも `is_booking_admin()` を検査します。
補助検査関数は個人情報を返しません。service_roleを使う設定保存APIは追加していません。
直接のテーブル更新にもトリガーが適用され、設定の最終状態をコミット時に検査します。予約と矛盾する場合は部分更新も確定しません。

適用の準備・確認順序（別途、実行の案内を受けてから行う）：

1. 接続先が `line-booking-test` であること、現在の営業設定とテスト予約が確認できることを確認します。必要なバックアップを保持します。
2. 003の全文をSQL Editorの新規クエリで実行します。新しい列・関数・トリガーを追加するため、一度だけの適用を想定しています。エラー時に既存テーブルを削除したり、部分だけ実行したりしないでください。
3. 新コードをMacに取り込んで再起動し、管理者の設定読み込み・保存、矛盾する設定の拒否、一般ユーザーの拒否、空き時間への反映を確認します。Data APIの標準権限への置き換えは行いません。

## 営業設定の条件付き更新修正（004・テストDBで適用済み）

Supabase側で `21000: DELETE requires a WHERE clause` が記録された場合、003の条件なしDELETEが保護機能に拒否されています。
003だけでは営業設定の保存が失敗する環境があります。003を編集・再実行せず、追加の `004_business_settings_filtered_writes.sql` を使います。
新規構築でも001→002→003→004の順です。

004は保存関数だけをCREATE OR REPLACEし、設定・予約の行自体は変更しません。003が未適用なら停止します。
管理者チェック・既存RLS・リビジョンの競合検出・予約との整合性検査・トランザクション・ロックは維持します。
関数の所有者と既存の実行権限を維持し、PUBLIC/anonへの権限追加や削除保護機能の無効化は行いません。

修正後の保存処理：

- 新設定に含まれない曜日だけを条件付きDELETEし、残る曜日はUPSERTで時刻を更新します。
- 新設定に含まれない休業日だけを条件付きDELETEし、同じ日付は必要に応じて理由を更新します。
- 既存予約を削除・キャンセルする処理はありません。予約と矛盾する場合は全体をロールバックします。

最初の適用先は `line-booking-test` です。全文のレビュー・適用案内を受けるまではRunを押しません。本番 `line-booking-system` には適用しません。
004の適用後はアプリコード・環境変数の変更やサーバー再起動なしで、設定の再読み込み後に動作確認できます。
ローカルPostgreSQLでの検証はSupabaseの削除保護拡張そのものを再現するものではありません。別途、利用者によるテスト専用Supabaseでの手動確認で、004適用後の保存成功・休業日の反映と解除・既存予約保護を確認しました。

## 月間カレンダー用の読み取り関数（005・実際のDBには未適用）

`005_booking_month_calendar.sql` は管理者専用の `get_booking_month_counts(date)` を追加します。
予約の開始日時を日本時間の日付で集計し、月内の全日付について確定・来店済み・キャンセル済みの件数だけを返します。
個人情報・予約ID・予約時刻は返しません。テーブル・トリガー・既存予約・営業設定・既存のテーブル権限・RLSは変更しません。
関数はSTABLE・SECURITY INVOKERで、PUBLIC/anonの実行権限を取り消し、authenticatedだけに実行を許可し、内部でも店舗管理者か検査します。

適用先はまずテスト用 `line-booking-test` です。001〜004が適用済みなら005だけを全文で実行します。適用済みSQLの再実行や、Data APIの標準権限への置き換えはしません。
この関数の初回追加だけを想定しており、同名関数が既にある場合は置き換えずエラーになります。新規構築は001→002→003→004→005の順です。

APIの行取得上限に依存せず、DB内の1つの集計SELECTで0件の日も返します。表示対象は1000年1月〜9998年12月で、引数は必ず月初日です。
PostgreSQL17のネットワークなしの一時DBで、月境界・うるう日・年越し・1205件のキャンセル履歴・非管理者拒否・読み取り専用性など9場面を検証します。
005の実際のSupabaseへの適用とAuth/PostgRESTを組み合わせた確認は未実施です。
