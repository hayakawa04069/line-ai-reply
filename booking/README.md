# 予約アプリ（1店舗向け試作品）

既存のLINE AI返信とは別のNode.jsプロセスです。外部パッケージのインストールは不要です。
既存の `server.js`・`npm start`・Render設定は変更しません。

## できること

- お客様：メニュー選択、月間カレンダー、空き時間選択、お名前入力、LINE本人確認、予約確定・完了画面
- 店舗：管理者ログイン、日本時間の日付別予約一覧、確認画面付きの予約キャンセル、ログアウト
- Supabaseの既存テーブルを使用。追加SQLの適用は不要です。

予約の日時変更、営業設定画面、決済、通知、複数スタッフにはまだ対応していません。
既存のAIが予約登録を行う機能も追加していません。LIFFリンクから予約ページを開く方式です。

## 1. 環境変数を用意

ルートの `.env.example` に予約用の変数名を追記しています。
既に `.env` がある場合は上書きせず、予約用の項目だけ追加してください。なければ `.env.example` を `.env` にコピーします。
APIキーやパスワードはGitHubやチャットに貼らないでください。

| 変数名 | 設定するもの |
| --- | --- |
| `SUPABASE_URL` | `line-booking-system` のProject URL（HTTPS） |
| `SUPABASE_ANON_KEY` | 同プロジェクトの従来形式の `anon` APIキー |
| `SUPABASE_SERVICE_ROLE_KEY` | 同プロジェクトの従来形式の `service_role` APIキー。サーバー専用・公開禁止 |
| `LINE_LOGIN_CHANNEL_ID` | LINEログインチャネルのチャネルID。Messaging APIチャネルのIDとは別 |
| `LIFF_ID` | 上記LINEログインチャネルで作成したLIFFアプリのID |
| `BOOKING_ORIGIN` | 予約アプリのURLのオリジン。ローカルなら `http://localhost:3001`。末尾の `/` やパスは付けない |
| `BOOKING_PORT` | ローカルは `3001`。未設定の場合も3001 |

SupabaseのProject Settings → API Keysで `anon` / `service_role`（Legacy API Keys）を確認します。
この試作品は従来形式のJWT APIキーを前提にしています。`sb_secret_...` など新形式のキーへの対応は未検証です。
`service_role` はRLSを迂回できる強いキーなのでサーバーにだけ置き、HTMLやJavaScriptには書きません。
既存の `LINE_CHANNEL_SECRET`、`LINE_CHANNEL_ACCESS_TOKEN`、`OPENAI_API_KEY`、`PORT` は変更しません。

## 2. Supabaseに店舗管理者を登録

`001_initial.sql` と `002_example_settings.sql` は適用済みのため、再実行しません。

1. Supabase AuthenticationでEmail/Password認証を確認します。
2. 店舗用のメールアドレス・パスワードでユーザーを作成します。メール確認が必要な設定では確認も済ませます。
3. そのユーザーのUUIDを確認し、SQL Editorで次だけを実行します。

```sql
insert into public.booking_admins(user_id)
values ('ここをAuthenticationのユーザーUUIDに置き換える'::uuid)
on conflict do nothing;
```

一般のお客様のSupabase Auth登録は不要です。一般向け新規登録は無効にしてください。
Authenticationにユーザーがあるだけでは店舗管理者にはなりません。`booking_admins` への登録が必要です。
店舗管理画面にはSupabaseのダッシュボード用パスワードではなく、今作った店舗用ユーザーのパスワードでログインします。

## 3. LINEとLIFFの準備

1. LINE Developersで、既存のMessaging APIチャネルと**同じプロバイダー**にLINEログインチャネルを用意します。
2. そのログインチャネルでLIFFアプリを追加します。スコープは **openid** を必須とし、サイズはFullを推奨します。
3. `LINE_LOGIN_CHANNEL_ID` と `LIFF_ID` を予約アプリの環境変数に設定します。チャネルシークレットはこの予約アプリでは不要です。
4. 実際にLINEで試す段階で、本番とは別の検証用HTTPS URLを用意します。今回は公開・デプロイしていません。
5. LIFFのエンドポイントURLをそのURLの `/` に、`BOOKING_ORIGIN` をそのオリジンに設定します。ページを開くときは `https://liff.line.me/LIFF_ID` を使います。
6. 開発中のLINEログインチャネルはテスターの権限・公開状態も確認してください。

ローカルHTTPだけではLIFFの実機動作確認は完結しません。既存の本番Webhook URLを変更する必要はありません。
本番アカウントのリッチメニュー設定を変更するのは公開確認後にします。

## 4. 起動

リポジトリのルート（`line-ai-reply` フォルダ）で実行します。

```sh
node --env-file=.env booking/server.js
```

ローカルでは予約用のポート3001を使い、既存AI返信のポート3000と分離します。
ブラウザーで `http://localhost:3001/` を開くとお客様用ページ、`/admin` は店舗用ページです。
ローカルURLの確認は自分のブラウザーで行い、LINEに登録するURLには検証用HTTPS URLを使用します。

既存の `npm start` はこれまでどおりAI返信だけを起動します。

## 店舗管理画面で予約をキャンセルする

1. `/admin` に店舗管理者としてログインし、対象の日付を選択します。
2. 確定済み予約の「予約をキャンセル」を押します。
3. 確認画面のお客様名・メニュー・日時を確認します。「戻る」またはEscapeキーでは何も変更しません。
4. 「キャンセルを確定」を押します。処理中は連打と画面内の日付変更を防ぎます。
5. 一覧に「キャンセル済み」と表示されます。予約・顧客の行は削除しません。

更新APIは `POST /api/admin/reservations/:id/cancel` です。本文は一覧に含まれる `updated_at` をそのまま `updatedAt` として送る形式です。
サーバーは管理者権限を確認し、管理者本人のJWTで `status=confirmed` と更新日時が一致する行だけをPATCHします。変更内容は `status=cancelled` のみで、サーバー専用キーは使いません。
更新日時には小数点以下6桁の場合があるため、画面側で丸めずに送信します。

- 確認中に他の担当者が予約を変更した場合：409を返し、一覧を再取得します。新しい内容を確認してから操作してください。
- 別の担当者が先にキャンセルした場合・同じ操作の再送：現在のキャンセル済み状態を返し、重ねて変更しません。
- 来店済み：キャンセル操作を拒否します。存在しない、またはRLSで見えない予約は404になります。
- 通信失敗：成功とは表示せず、一覧を再取得します。DBだけ更新済みの場合があるため、再取得した状態を確認します。
- 権限切れ：ログイン画面に戻し、予約一覧と確認画面内の個人情報を消去します。

既存の空き時間APIとDBの排他制約はキャンセル済み予約を除外しています。更新が完了すると、営業時間・受付期間などを満たす枠は次の空き時間取得から再び予約可能です。すでに開いているお客様画面は日付を選び直して最新情報を取得してください。
新しいテーブル・SQL適用・RLSの緩和は不要です。自動通知とキャンセル取り消し機能はありません。

## 権限・予約の仕組み

- 公開APIはメニュー・店名・空き時間だけを返します。お客様の名前・電話番号・LINE ID・他人の予約一覧は公開しません。
- LIFFのIDトークンをLINEの検証APIへ送り、チャネルID・期限・発行元も確認します。送られた顧客IDだけを信用しません。
- 顧客IDは検証済みLINEユーザーIDからサーバーで決定します。お名前は本人が入力します。
- 予約登録のみサーバー専用キーを使用します。料金・所要時間・営業時間・休業日の最終判定は既存DBのトリガーに任せます。
- 排他制約を変更せず、同時予約はDBが拒否します。空き状況表示は確定を保証しません。
- 同じ確定操作の再送は同じ `request_id` を使い、その本人の予約だけを再取得します。二重クリックも画面で抑止します。
- 管理者ログインはSupabase Authで検証し、`is_booking_admin()` で店舗権限を確認します。一覧取得にもその本人のJWTを使うため、既存RLSが適用されます。
- 管理者権限はAPIを呼ぶたびに確認します。`booking_admins` から削除すると次のAPI操作でアクセス拒否になります。
- JWTはサーバーのメモリ内だけに保持し、ブラウザーにはHttpOnly・SameSite CookieのランダムなセッションIDだけを渡します。HTTPSではSecureも付きます。LocalStorageにトークンを保存しません。
- セッションは最大1時間で期限切れになります。サーバー再起動でもログアウトします。複数台運用にはセッションの共有化が必要です。
- 更新APIは同じオリジンからのリクエストだけを許可します。ログイン試行・予約登録には簡易的な回数制限があります。
- 受信本文やAPIエラー詳細をログに出しません。DBエラーに含まれ得る個人情報を画面へ返しません。

管理画面では当日に開始する予約をキャンセル済みも含めて一覧表示します。名前とメニューを表示し、電話番号・LINE IDは取得しません。
Supabase側にはお名前とLINEユーザーIDを保存します。利用者にその目的を案内し、実運用前に保存期間・削除手順を決めてください。

## テストと未確認事項

```sh
npm test
```

既存24件（AI返信7件・予約アプリ17件）とキャンセル用12件、計36件を実行します。テストは外部APIを模擬し、キーや本番DBを使用しません。
空き枠計算、LINE本人確認、顧客ID偽装拒否、重複エラー、同一リクエストの再送、管理者認証・権限取り消し、Cookie、CSRF、秘密情報の非公開を確認します。
別途、模擬APIとChromiumでスマートフォンの予約確定、管理者ログイン・一覧・再読込・ログアウト、入力文字列のHTML化防止、画面の横はみ出しがないことを確認しました。

キャンセル用テストでは、本人のJWT、条件付き更新、更新日時の精度、二重操作、同時操作、応答喪失後の再送、変更済み・来店済みの拒否、権限・入力・CSRF、空き枠の復活を確認します。DBの動作は模擬するため、PostgreSQL自体の同時実行・RLSを証明するものではありません。

Python PlaywrightとChromiumがある環境では、任意で次の画面テストも実行できます。

```sh
python3 booking/test-support/cancellation-browser.py
```

成功、他の担当者による変更、通信失敗、更新後の応答喪失、権限取り消しの5場面を確認します。「戻る」・Escape・連打防止・確認画面の内容・HTML化防止・キャンセル済み表示も検証します。
テスト用Node.jsプロセスには本番の環境変数を渡さず、ブラウザーもローカル以外への通信を遮断します。Playwrightがない環境ではこの追加テストの実行準備が必要ですが、`npm test` は引き続き外部パッケージ不要です。

**キャンセル機能の実際のSupabaseでの更新・RLSとの結合確認、およびLIFFの一連の操作確認は未実施です。** これまでのSupabase読み取り確認と、キャンセル更新の確認は別です。
設定後はまず架空データで、予約→店舗一覧への反映、同じ時間への同時予約の拒否、非管理者でのアクセス拒否を確認してください。
本番の個人情報を使わず、既存のRenderへはデプロイしません。

## 試作品の制限

少人数の検証向け・1プロセスでの運用です。回数制限とセッションはメモリ内で再起動時に消えます。
リバースプロキシ越しのIP制限は複数利用者で共有される場合があります。本公開前にプロキシ構成に合う制限や不正予約対策を整えます。
外部APIの応答が途切れた際、予約がDBに保存済みの場合があります。まず同じ画面の確定ボタンで再試行してください。新しい予約操作に切り替える前に店舗でも確認します。
